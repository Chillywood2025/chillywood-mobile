## Reproduced current-source gap: post-commit Start truth and recovery

Source: `_lib/chat.ts:1100–1141` receives a successful begin/dispatch, then performs a final `getChatThread`. That helper returns null on either a database read error or missing row. The API throws `Unable to refresh Chi'lly Chat call state.` The actual screen's generic catch at `app/chat/[threadId].tsx:2430–2446` unconditionally says: `Delivery status: invite failed. Call was not started and receiver notification was not sent.` It clears outgoing projection and releases the Start operation even though the known invite/dispatch already exist.

The local probe composed the actual API with the existing full mounted-screen harness, withheld the independent Realtime notification, and supplied only the final read failure. A temporary source override exposed `callDeliveryStatus` through a layout observer; it did not replace any production handlers, conditions or state setters. Both transport-error and null-row cases produced:

- One confirmed `beginChillyChatCall` receipt with `created=true`, current fixture invite `ringing`, one room.
- One dispatch receipt with `status=sent`, `pushSent=true`, `notificationCreated=true`.
- Exactly two thread reads, no terminal cleanup, no capture.
- UI error `Unable to refresh Chi'lly Chat call state.`, closed panel, null active invite, `callBusy=false`, and the false never-started/never-sent delivery assertion above.

The intended truth assertion fails against unchanged `191ffb8e`. The original controlled counterexample intentionally failed its desired truthful-copy assertion. Native/dispatch/database boundaries are controlled; there was no real production call.

This is a new concrete code-only gap in the Start/setup/reuse obligations, not proof that historical DE03 (diagnosed throttling), any old physical FAIL, or the unexplained PR #576 browser failure had this cause. Existing PR #585 tests cover delayed successful readback and stale responses, but not this post-commit failed read.

Bounded source repair in this candidate:

1. Distinguish confirmed committed-start readback failure from definite pre-start failure and unknown begin outcome. Preserve the already-known invite/room/dispatch receipt in a typed, account/session/thread-owned result instead of erasing it in generic failure copy. The result distinguishes `ready` from `readback_pending`; the pending receipt carries domain state, not an exception or customer copy. Public failures continue through the existing directly constructed app-owned errors and sanitizer.
2. Say that the call was requested but its current state could not be refreshed. Do not assert never-started or never-sent when those are positively known; do not promote the old ringing receipt to current accepted/active state.
3. Offer/use read-only reconciliation of that exact current thread/invite before another Start. Do not automatically call begin/dispatch again, cancel a possibly answered call, clear a newer call, or start media from the cached receipt. Preserve #585's synchronous ownership/late-completion fences and ordinary deliberate retry after a definite pre-start failure.
4. Regression set: successful begin/dispatch followed by error/null read; recovered current ringing vs accepted vs terminal state; replacement account/session/thread and newer call while recovery is pending; repeated recovery taps issue no duplicate begin/dispatch; definite room/begin failure retains useful rate-limit copy and deliberate retry. If scope expands to unknown begin/dispatch, require distinct evidence rather than conflating it with the proved case.

The candidate changes only the API receipt/readback boundary, owned screen recovery and controlled tests. A confirmed receipt keeps the original synchronous Start barrier. Refresh call status performs read-only thread/invite reads; it never begins/dispatches/cancels a call or opens media. Current, coherent server state releases recovery; stale owners/projections cannot apply it. Unknown begin/dispatch outcomes are not relabeled confirmed.

The read-only claim applies to the new receipt recovery, not the entire existing Start path. Original `getChatThread` calls, including the post-begin readback, retain their default stale-call reconciliation and possible `clear_stale_chilly_chat_thread_call` RPC. The controlled error/null probes fail before that reconciliation and thus have zero cleanup calls. A separate API assertion exercises the successful default readback's pre-existing cleanup RPC; the same fixture through receipt recovery performs no cleanup. This repair does not remove that established successful-Start behavior or add cleanup authority to the new recovery control.

If the exact refreshed old invite is terminal while the current thread retains a room link, recovery preserves that raw link, clears only the pending receipt, and says that the requested call ended but the remaining call entry needs current-state checking. Both Start buttons remain disabled by the link. It does not install an invite or open the panel/media. A subsequent explicit Open Call uses the existing invite revalidation path; it must not borrow the terminal receipt as current media authority.

An additional adversarial pass caught a callback-lifetime hole in the unpublished repair, not a separately established baseline or physical failure. Successful recovery originally released Start ownership without retiring pre-recovery Start callbacks. Those callbacks still captured an empty room and idle state. Invoking one before or after the fresh accepted-room projection committed reused the room through the actual helper and opened one controlled media stream and membership join, despite the fresh Start controls being disabled. In that accepted-room fixture, begin/dispatch remained exactly once. After terminal/no-link recovery, the old callback instead created, began and dispatched a second call. No production call, notification or capture was initiated. The final repair synchronously retires those callbacks using the settled recovery operation identity and releases Start ownership only after the fresh thread projection commits. Retained callbacks cannot read or reopen a recovered room; only the new committed callback can carry a deliberate fresh Start after terminal/no-link recovery. Linked rooms still require the explicit Open Call path.
