## Why prior automation missed these defects

1. A model of participant state did not render the production tile. The new
   React tests transpile and render the complete production component. Native
   view hosts remain substituted. Retained streams and LiveKit references are
   deliberately present during camera-off/disconnection tests.
2. Starting from an already-active hook missed background initialization. New
   tests mount the production lifecycle from background without injected peers,
   streams or live state. Native permission/capture and API boundaries remain
   controlled; those tests prove JS behavior only.
3. Successful synthetic SDK promises are weaker than real native receipts.
   In pinned `@livekit/react-native-webrtc` 144.0.0, JS `MediaStreamTrack.stop()`
   marks its track ended without awaiting native capture shutdown. iOS capture
   start logs native errors without exposing equivalent failure to JS. These
   are inspected boundary gaps, not proven causes of this run's failures.
   Existing native sender-acknowledgment patches must remain intact.
4. CallKit event and route stubs cannot establish real system action delivery,
   app activation, navigation or audio routing. A queued Answer, fulfilled
   server request or connected transport is not a completed audible call.
5. High-volume call setup can hit legitimate throttling. Every attempt needs
   the original error and stage; generic UI copy obscured this distinction.

The new regression tests were first run against the old behavior: 10 of 11
grid cases failed, background microphone restoration failed, and both
rate-limit message cases failed. They pass with the corresponding source
repairs. This provides a concrete negative control against tests that merely
agree with a copied implementation.

## Stronger validation, with explicit proof boundaries

No finite suite is bulletproof. Use independent oracles at each actual boundary:

| Layer | Required observation | Cannot establish |
| --- | --- | --- |
| Production component | Render actual camera/connection state with stale stream references; assert visible copy and whether media view exists | Camera frames, capture privacy, native RTCView behavior |
| Mounted production hook | Natural startup; deferred/failing permissions, acquisition and sender calls; End/account/room replacement at every async boundary; one current owner | OS suspension, actual device capture or speaker output |
| Real peer integration | Actual SDP/RTP; received audio samples and energy; decoded changing frames; mute produces measured silence while samples continue | iOS/Android SDK or hardware behavior when using Chromium and synthetic capture |
| Native generated source and compile | Exact dependency/plugin hashes, generated native diff, Swift/Kotlin compilation and native tests for actual receipts, cancellation and error paths | Installed distribution binary identity or physical media |
| Signed installed app | Both exact builds, OS versions, runtime/update identity, provider and call correlation; actual native action and lifecycle traces | Audible output or genuinely moving video without observing them |
| Physical end to end | Consenting observer hears an unpredictable phrase each direction; remote participant confirms changing motion and actual lens; route/Bluetooth challenges | Unexecuted matrix variants or a different candidate/provider |

Research basis (primary sources, accessed 2026-09-29):

- [Android foreground-service background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start):
  while-in-use permission and background service eligibility are distinct.
  A granted permission check alone does not establish that a microphone service
  may start from background. Preserve restrictions and test the actual entry path.
- [Android foreground-service types](https://developer.android.com/develop/background-work/services/fgs/service-types):
  verify declared microphone service type and applicable runtime prerequisites
  against the installed target SDK; record denied/ineligible outcomes explicitly.
- [Apple CallKit call lifecycle](https://developer.apple.com/documentation/callkit/making-and-receiving-voip-calls)
  and [audio activation delegate](https://developer.apple.com/documentation/callkit/cxproviderdelegate/provider(_:didactivate:)):
  configure audio for the call, then use the system's audio activation event to
  start call audio. Measure that boundary independently from Answer and routing.
- [W3C WebRTC statistics](https://www.w3.org/TR/webrtc-stats/): sample current,
  correlated stats over time. Packet/byte counts alone do not show decoded or
  rendered moving video. Collect `framesDecoded`, `framesRendered` where
  supported, received audio samples/energy, losses and freezes. Missing SDK
  fields are unavailable measurements, not zeros or inferred successes.

The testing requirements above are engineering conclusions from those contracts
and this evidence, not claims that the vendors guarantee this app works.
