# Connect dual-mode deployment cutover — not executed

Do **not** run the completion migrations and then deploy Edge functions as one assumed-safe step. Migration `20261101170000` removes creator-only account uniqueness. A previously deployed `upsert(... onConflict: creator_user_id)` can then fail **after** Stripe created an account. A current source checkout is not proof of the deployed bundle, and even a compatible old test observer can overwrite shared readiness until every writer is upgraded.

## Chosen approach: bounded setup-admission pause with positive drain

This is a deployment plan for the parent/operator after exact-head validation and explicit rollout approval; no deployment or provider mutation was performed here. Only Connect setup/status ingestion pauses, not unrelated app features. Keep all money rails, live onboarding/observation qualification and financial automation OFF/unseeded throughout.

1. **Inventory actual deployed writers before mutation.** Save sanitized function IDs/versions/bundle hashes, gateway/JWT configuration and source evidence for `stripe-connect-account`, `stripe-connect-onboarding-link`, `stripe-connect-account-sync`, `stripe-connect-webhook`, and `stripe-connect-live-observation-webhook` if it exists. Search actual bundles and database callers for every account/eligibility writer, not just endpoint names. Record whether each uses INSERT, exact-row UPDATE or creator-only UPSERT. Stop if an unaccounted writer exists. Inventory pending account-create audit requests and retryable webhook receipts; do not export private payloads or signed links.
2. **Pause admission before any incompatible DDL.** The reviewed `ops/connect-mode-cutover/paused-entrypoint.ts` is a no-import/no-body-read/no-provider/no-DB guard. In an isolated reviewed deployment staging worktree, deploy this exact artifact under each existing writer name, preserving its actual gateway/JWT settings. It returns 503 + Retry-After and a versioned admission marker, never a misleading webhook 2xx. Existing signed events therefore remain retryable. Record each deployed version/hash. A failed or uncertain deployment requires read-back before retry, never assumed success. This is a temporary deployment artifact, not a new public endpoint or a credential change.
3. **Establish a positive drain.** Verify the pause marker through every exposed ingress/region and that no new old-version invocation is admitted. Record the latest accepted old-version invocation timestamp only after routing propagation is confirmed. Inspect invocation completion/termination and existing request/audit evidence. The legacy `stripeRequest` has no source-level fetch timeout, so a client 504 is not proof that its provider call ended. [Supabase's current limits](https://supabase.com/docs/guides/functions/limits) state worker wall time of 150 seconds free / 400 seconds paid and a separate 150-second idle response timeout. Verify this project's actual applicable runtime limit; wait beyond that bound plus a reviewed margin **from the last confirmed old-version admission**, and require no later old admissions and positive completion/termination evidence. Seven minutes alone is not a drain certificate. Missing propagation, invocation or termination evidence blocks the DDL; do not guess or bypass it.
4. **Resolve unknown external creation outcomes while paused.** For each account-create requested audit without a conclusive bound account, retain the original invocation/audit/creator/mode/legacy idempotency-key provenance. Read existing Stripe accounts using the correct platform and test/live credential scope; enumerate complete bounded/resumable histories and match exact metadata (`creator_user_id`, `chillywood_provider`, `chillywood_provider_environment`) and controller/account facts. Read back the exact matched account before any separately reviewed binding repair. A timed-out POST or expired idempotency window never authorizes another creation POST. Zero or multiple matches remain unresolved/quarantined, not “no account”; no account deletion, conversion or replacement. If a legacy unknown cannot be conclusively resolved, retain the setup pause; resuming other creators would require a separately reviewed per-creator quarantine rather than assuming one exists. Never resume a handler that might create a duplicate account. No provider writes are part of this reconciliation step.
5. **Apply and verify schema while guards remain deployed.** Confirm the exact hosted migration baseline and run only the approved forward sequence, including the distinct bindings, atomic eligibility conflict repair, and all-mode setup admission migrations. Verify both distinct account rows preserve original IDs; mode-binding/consent tables are private/immutable; exact API grants and current-session checks remain; positive test readiness cannot carry into live; negative creator holds remain; money/qualification controls stay off. Never disable uniqueness or RLS temporarily to make an old writer work.
6. **Deploy compatible final bundles while setup remains non-live.** Deploy the exact validated current Edge bundles; read back their versions/hashes and verify all shared dependencies are included. The steady-state implementation uses INSERT for new accounts and exact row/account/mode/timestamp CAS UPDATE for observations, not creator-only UPSERT. Ordinary non-testers cannot fall back to test account creation; exact adult/creator/legal/current-session and existing tester authority are required. Live onboarding stays unavailable until its separately qualified policy and scoped provider setup exist. Reconcile/replay only authenticated retryable callbacks after every writer is compatible; duplicates must remain idempotent. Do not use real account creation as a deployment smoke test.
7. **Exit checks and rollback.** Run read-only owner/creator status probes, exact-current-session negative probes, callback receipt checks and configuration/schema invariants. Confirm no old bundle is serving and no unmatched legacy creation remains. Record actual versions and migration IDs, not just source commits. If any new handler fails, restore the reviewed no-write guard, not the old creator-only writer; schema rollback/account deletion is prohibited. A separate reviewed forward fix is the recovery path. Keep unrelated app features available and explain the temporary setup pause plainly.
