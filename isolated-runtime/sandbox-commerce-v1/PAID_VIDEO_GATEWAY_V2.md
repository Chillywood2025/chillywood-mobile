# Paid Video gateway v2 — inactive source

This separate profile preserves the frozen v1 source and proofs. It is not an
installation, cloud/provider qualification or release approval. All live money,
payouts and cashout remain off.

Install `paid-video-gateway-v2.sql` after the complete protocol3, media, commands,
upload and `paid-video-access.sql` modules and before `permissions-finalize.sql`,
in the same installation transaction. It starts disabled and seeds no key or
qualified route. Existing source profiles remain unchanged.

The fresh combined profile must install `paid-video-install-context-v2.sql`
after the baseline graph/delivery modules, then use
`paid-video-install-grant-v2.sql` immediately before the frozen media/upload/
commands group and `paid-video-install-revoke-v2.sql` immediately after it.
The protocol3 modules retain their own bounded CREATE intervals. Use the same
grant/revoke pair around `paid-video-access.sql` and `paid-video-gateway-v2.sql`,
then apply baseline `permissions-finalize.sql`. Both grants require the original
fresh transaction/session and disabled lifecycle. A deferred constraint aborts
COMMIT if CREATE remains granted, the gateway is missing/enabled or the lifecycle
was activated. This supplies the new function owner permission required by a
non-superuser installer without changing frozen function definitions.

The additive ACL change revokes public `isolated_paid_video_v1`,
`isolated_paid_video_upload_v1` and `isolated_paid_video_access_v3` from both
authenticated and service roles. Their frozen private implementations are
reused behind the stronger v2 entrypoints. The dedicated range gateway calls
only `isolated_paid_video_gateway_access_v2`: current Auth, exact grant/raw
receipt, current Test Store holds and exact scanner/media identity are checked
by protocol3; the wrapper additionally requires the immutable upload receipt.
The server checks before origin I/O and before releasing bytes. Each request is
bounded to five seconds and each range to 512 KiB. Already-buffered bytes cannot
be recalled.

The generic `authorize_resource_delivery` graph was already private, with no
public RPC and no service-role EXECUTE grant. This profile reasserts those
existing revokes rather than replacing its implementation or claiming an
exposed historical bypass. Core-owner reuse for other products remains valid;
the dedicated range gateway must use the stricter receipt/hold-aware wrapper.

All three Edge entries default unavailable unless their explicit server flag
and configuration exist. No `config.toml`, installer or release is changed.
Server configuration includes a private S3 route and separate upload-verifier
key. R2 remains a distinct uninstalled adapter; no S3 version ID is fabricated.

## Client contract

`paid-video-contract-v2.json` is generated by
`node tests/paid-video-gateway-schema.mjs --write`; `--check` detects drift.
The v1 contract is never widened. JSON authoring uses
`/functions/v1/isolated-paid-video-authoring-v2`, captured Bearer authorization,
public Supabase API key, and exact body:

```json
{"protocol":"isolated-paid-video-v2","command":"capability.read","requestId":"UUID","expectedSessionId":"actual JWT session UUID","configurationDigest":"compiled dedicated V3 profile SHA256","payload":{}}
```

The digest identifies a separately qualified native configuration; it is not
device attestation. Responses carry the same digest and a bounded
`capabilityExpiresAtMs`. The server rechecks every action independently.
`resource.read` adds optional owner `data.offer` for restart/new-device discovery.
Studio entries remain history; obtain fresh `upload.read` before transfer.

A separate immutable v2 request journal binds each successful authoring mutation
to its original configuration digest, session, command and payload. Recovery
returns `originalConfigurationDigest` and the unchanged private canonical
`originalPayload` (`protocol: isolated-paid-video-v1`, request UUID and exact
command fields). It never inserts a digest into that frozen payload or adopts
an unbound legacy request. Changed configuration/session cannot replay the old
mutation; read-only recovery preserves its original identity.

Raw transfer uses `/functions/v1/isolated-paid-video-upload-v2/<uploadId>` and
headers `x-chillywood-auth-session`, `x-chillywood-request-id` and
`x-chillywood-native-configuration`. The request UUID is a distinct durable
transfer attempt, never the reserve command UUID. PUT accepts only raw
`video/mp4` with the exact network Content-Length. The server owns the route,
key and incarnation. One permanent create lease permits one conditional PUT;
unknown outcomes never resend or allocate a replacement key. PUT response
`scpv-transfer-v2` always says `verificationRequired:true`.

GET on the same path is read-only. It authenticates the current session and
reads the exact original transfer's whole private object, verifying the actual
SHA256/length and S3 version before and after current authority checks. It
returns either a recorded receipt or an HMAC-signed public observation. The
observation contains actor/current session, original transfer/session, upload,
incarnation, hash, length, actual version, verifier, profile and expiry; it
contains no bucket, key, URL or credential. It expires within 30 seconds.

POST on the same path accepts only `scpv-reconcile-v2` with exact
`observationRaw` and `signature`. SQL independently verifies the separate HMAC,
freshness and every immutable binding before recording a receipt. Duplicate
exact reconciliation is idempotent. Lost POST responses recover through GET.
The receipt includes `userId` and `originalSessionId`. A new current session
can read existing receipts or probe the original unknown transfer without
changing its durable request identity.

Owner-only `upload.read` includes `data.transfer`, either null or the exact
retained `{requestId, originalSessionId, configurationDigest}`. A new device
may adopt that descriptor only for read-only recovery, never for another PUT.
Null is not evidence that an interrupted operation never ran. Signed probes
and receipts also retain `originalConfigurationDigest`; the probe's separate
`configurationDigest` identifies the currently qualified recovery profile.

Finalization requires that receipt. Publication additionally requires actual
clean scanner evidence and explicit moderation matching its exact object
version; the receipt alone grants no access. The existing scanner's version is
checked against the object receipt before publication and delivery.

Authenticated playback path remains
`/functions/v1/isolated-paid-video-range-v1/<resourceId>/<grantId>`, with captured
Bearer/public API key/current session header and an optional single Range.
There are no signed or public storage URLs, cache authority or client-selected
storage coordinates. Query strings and extra path segments are rejected.

Every successful 206 response exposes `x-chillywood-media-protocol` equal to
`scpv-range-metadata-v2`, and `x-chillywood-` headers ending in `resource-id`,
`grant-id`, `asset-id`, `incarnation`, `sha256`, `byte-length`,
`resource-revision`, `profile` and `authorized-until-ms`. The profile is
`scpv-mp4-h264-aac-v1`. The immutable media tuple must match the private object
and both current-access reads. The deadline is the minimum of both SQL
authorization deadlines, JWT expiry and request start plus five seconds; an
expired deadline suppresses the response. All these nonsecret headers and
Content-Range, Content-Length and Accept-Ranges are explicitly CORS-exposed.
The first-byte `Range: bytes=0-0` request takes the identical authority path.
Sequential read-only renewal may shorten a client lease; it cannot revive a
lease that already expired, and the response is never reusable server authority.

## Qualification boundaries

The native SQL fixture uses actual PostgreSQL and production gateway source,
but explicitly synthetic Auth/provider/native/object-transport facts. The
separate HTTP profile uses actual local Auth and PostgREST. Neither establishes
cloud provider behavior or deployed availability. A qualified actual private
storage route, scanner service, independent verifier key, protocol3 native
profile and Test Store provider/lifecycle controls remain required before
positive production capabilities or deployment can be authorized.
