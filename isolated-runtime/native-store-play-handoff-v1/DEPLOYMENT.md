# Forward Play preparation boundary

This package is an offline, deployment-unqualified preparation tool. It contains
no network client and cannot authorize a write, provider change, activation,
build, release, SKU or money operation. The immutable original 48 modules are
never reapplied. Only the unchanged handoff and settlement SQL and the narrow
boolean-only private reader are persistent forward changes.

## Source and identity

The fixed identity is `20261110021650_native_store_play_handoff_settlement_v1`,
generated by the official Supabase CLI 3.1.0. `deployment.sql` and
`deployment-artifact.json` preserve the exact version, name, body and SHA256
outside the automatic migration directory. `deployment-source.json` and
`deployment-allowlist.json` bind each forward module and exact normalized catalog
change. Eight existing function OIDs remain; only the named replaced CHECK may
receive a new OID. Triggers on old relations are part of the explicit allowlist.

`buildDeploymentEnvelope({baseline, source})` requires the exact frozen Git commit,
clean tracked source and byte-for-byte Git binding of the imported generator,
helpers, manifests, fixed body and source closure. The separately named local
fixture builder is unqualified test support, not a dispatch route. Rebuilding
the fixed artifact is a source change requiring review and CI.

## Before any dispatch

Apply and independently verify the earlier shared-exclusion migration first,
then collect a new Play baseline. Existing history must be strictly earlier than
the fixed Play version; a version or name collision is not a retry opportunity.

1. Verify the official transport binds project `bmkkhihfbmsnnmcqkoly`. A SQL
   comment, project string, caller boolean or local fixture does not prove it.
2. Coordinate an administrative-DDL and runtime-write hold through the operation.
   Verify runtime activation flags are absent. Read the existing journal/core
   private-state reader using its genuine read-only identity, repeatable-read
   transaction and original 5-second statement/transaction limits.
3. Collect `deployment-observe.sql` as one fresh genuine read-only
   repeatable-read snapshot. Split observations are not a baseline. The new
   transaction independently checks all current core controls and required empty
   core/native tables under the installation owner. No journal-owner interval or
   direct journal grant is added. The separate journal observation is not an
   atomic assertion about apply-time journal state; its no-drift qualification
   depends on the verified flags and coordinated hold.
4. Build the envelope from that exact snapshot and frozen source. Archive its
   exact bytes/hash and review them independently. A changed snapshot requires
   rebuilding and reviewing the archive. The fixed body remains identical.
5. Separately qualify the official Management API executor against that archive:
   exact project and bytes/hash, a durable once-only marker, one request, no
   redirect or automatic retry, bounded response/deadline, and independent
   readback. This executor is an unresolved prerequisite of this source package.

The envelope checks database `postgres`, server-start identity, managed
non-superuser writer, nonprivileged native owners, complete prior history,
original OIDs, money holds, exact old function/CHECK hashes and absence of all
added keys. The original transaction timeout is armed once. Privileges are
restored before original deferred source checks. A single manually versioned
history row records the fixed body in the same transaction. Checks after that
insert bind the exact independent receipt, all prior history, catalog and fresh
core state, so late failure rolls everything back.

## Bounded observations and recovery

Catalog observations accept at most 60,000 complete rows and OID observations
at most 35,000; their respective extra sentinel rows (60,001 and 35,001) reject
qualification. Full and retained digests use the same respective ceilings.
History reads at most 2,501 rows and rejects that boundary. A history array must
contain 1–1,024 non-null statements, each at most 8 MiB and at most 16 MiB together,
in a one-dimensional, one-based array before serialization. The total is limited
to 20,000 statements across history. That bound filters aggregate input before
returned hash arrays are constructed, rather than rejecting after oversized
output is built. Existing 12- and 14-digit historical versions remain verbatim;
the new identity stays exactly 14 digits with one exact source statement.
Nullable rollback arrays retain their 256-element limit and the same byte caps,
and nonempty rollback arrays must be one-dimensional;
null and empty arrays and their bounds are preserved distinctly. All six history
columns are retained, including created_by, idempotency_key and rollback. The
history schema is part of retained catalog and OID fingerprints. Its exact
six-column shape, postgres ownership, two validated PK/unique constraints,
ordinary permanent storage and no RLS/defaults/triggers/rules are required.
Unknown history write machinery fails closed rather than being adopted.
Money rows have the same 25,000 accepted maximum. Full
catalog/function/history bodies are never aggregated: each row is hashed first,
then fixed-width hashes are sorted with C ordering. Per-object function bodies
remain individual rows. ACL entries and internal FK trigger names use the same
normalization as local source derivation. The metadata read uses a 20-second
statement and one 25-second transaction budget; it invokes no private definer.

`classifyDeploymentOutcome` returns only `unchanged_observed`,
`exact_source_receipt_observed_committed_install_state_only`, or
`outcome_unknown`. Every result forbids retry and activation. Missing, partial,
malformed, wrong-source, wrong-target, restarted-server, wrong-receipt or changed
catalog/history observations fail closed. A receipt can attest guarded state at
commit, not independently current private runtime state. The new reader must be
called separately for that observation, with its genuine identity and original
5-second budget. A successful source review is not deployment permission.

## Local proof

The required settlement native path runs `deployment.native-cases.mjs` after its
own PostgreSQL cleanup. It launches only disposable local PostgreSQL 17.6 with
actual original48 and all forward SQL, OID padding and eight parity event
triggers. It verifies source/receipt framing, stale-baseline refusal, one budget,
late atomic rollback, original OID retention, exact receipt recovery, permission
restoration and the new reader. The ordinary deployment unit tests independently
cover artifact and API contracts. Fixture state is never used as a target
baseline or included in a deployment body.

The same mandatory path also runs `deployment-scale.native-cases.mjs` in a
separate sequential cluster. It replays the actual legacy migrations and their
multipart receipt arrays with original versions, then installs immutable48 and
proves complete forward success, forced late rollback, independent readback,
and real catalog counts below, at and above both ceilings. At-ceiling applies
that cannot fit the forward additions must roll back. These multiple local test
transactions have an aggregate process deadline; each individual transaction
retains the original 20-second statement and 25-second transaction budgets.
